system architecture

One loop, closed automatically.

Patchwork connects once and then runs quietly in the background — on every push, or on a schedule you set.

01 — ingest

Repository & webhook

Connects as a GitHub or GitLab App. Reads the AST, dependency tree and commit history on push or on a CRON schedule.

02 — detect

Scanner & AST engine

Semgrep and Tree-sitter run deterministic checks; an LLM reads across files for architectural anti-patterns.

03 — patch

Refactoring engine

Writes a minimal patch scoped to the one issue found — nothing else in the file is touched.

04 — verify

Sandbox test run

The patch runs against your real test suite inside an isolated container. Failing tests go back to the patch engine.

05 — ship

Pull request

Opens a PR with the vulnerability explained, a diff summary, and proof the tests passed.

04 loops back into 03 until every test passes — patches never ship unproven
how it works

What happens between a push and a pull request.

1

Repo ingestion & parsing

Patchwork connects through GitHub App or GitLab webhook permissions. Every push — or a nightly CRON run — triggers a fresh read of the AST, the dependency graph, and recent commit history.

2

Vulnerability & anti-pattern detection

Deterministic static analysis catches the known offenders instantly — hardcoded secrets, SQL injection vectors, prototype pollution. A second pass uses AI to read across multiple files at once, where race conditions and unhandled promise rejections actually hide.

Semgrep Tree-sitter SonarQube rules
3

Automated fix generation

The patch addresses the one issue it found. Surrounding logic, formatting, and unrelated functions are left exactly as your team wrote them.

4

Sandboxed verification

Before anything reaches your repo, the patch runs inside an isolated container against your existing test suite. A failing run sends the error log straight back to the patch engine, which revises and tries again.

npm test pytest cargo test
5

Clean pull request

The PR explains the vulnerability in plain language, includes a diff summary, and shows the passing test run — so review takes minutes, not a meeting.

detection

Two engines, because one alone misses things.

Deterministic rules catch what's known. Reading across files catches what's structural.

static analysis

  • Hardcoded secrets and API keys
  • SQL injection vectors
  • Prototype pollution
  • Known-CVE dependency versions
  • Instant, deterministic, no false starts

ai ast analysis

  • Architectural anti-patterns across files
  • Race conditions between services
  • Unhandled promise rejections
  • Context a single-file linter can't see
  • Reasoning, not just pattern matching
